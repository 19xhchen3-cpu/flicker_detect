# moudle1 检测性能优化分析

## 1. 目标与口径

目标是降低 `moudle1.py` 的**每轮计算时间**。两种口径：

- **单次满窗检测**：一次 `detect_window()` 的耗时；
- **滑窗逐帧检测**：`HistoryBuffer.push_frame()` + `detect()` 每帧的耗时
  （对应前端每帧出一次检测结果的调用方式）。

内存开销允许适当增大，不限制预分配和持久状态。

**代码形态定位**：`moudle1.py` 当前为 Python 原型，按
`docs/pure_logic_detector_design.md` 设计为**可直接翻译成嵌入式 C++**——
核心链路只使用显式循环、一维数组和固定 shape，不依赖 NumPy/OpenCV。
因此优化方向以最终 C++ 形态为基准：优先选择在 C++ 中依然成立、且能让
Python 原型与 C++ 实现逐行对应的方向；纯 Python 特有的开销（如
`float()` 函数调用）仅作为原型清理处理，不夸大其移植收益。

> 说明：本文第 4 节按**改动重量**从重到轻排列（重 = 架构/算法级改动或
> 面向 C++ 移植的核心策略；轻 = 局部小改或原型层清理）；第 6 节按
> **风险与依赖**给出实施顺序，两种口径不同。

## 2. 当前基准

用 30fps/50Hz 配置（`B=192`、`H=30`、`group_size=4`、`G=9`、`P=3`）测量
（临时基准脚本，未纳入仓库）：

| 口径 | 中位数 | 最小值 |
| --- | ---: | ---: |
| 单次满窗检测 | 12.17 ms | 5.93 ms |
| 滑窗逐帧检测（push + detect） | 13.34 ms | 5.99 ms |

每帧耗时约 13 ms，主要瓶颈在满窗重算：每帧都对 192 块 × 9 组重新计算
差分、符号、斜率、计数和 CV。

## 3. 每轮计算量分解

以干净周期信号（全部组有效且主导）为例，单个窗口内大约：

| 阶段 | 计算量 | 说明 |
| --- | ---: | --- |
| 1. 特征构建 | B×G×P ≈ 5184 | 每个差分做 2 次 `float()` 转换、2 次槽位索引、减法、`abs`、符号判断 |
| 1. 闭合斜率 | B×G ≈ 1728 | 每组再做 2 次 `float()` 转换 |
| 1. 符号编码 | B×G×P ≈ 5184 | 只对有效组做条件短循环 |
| 2. 主导计数 | B×G ≈ 1728 | 每组一次计数 |
| 2. 主导成员收集 | B×G ≈ 1728 | 收集进入 CV 的组 |
| 3. CV 第一趟 | B×d×P ≈ 5184 | 累加振幅求均值 |
| 3. CV 第二趟 | B×valid×d ≈ 5184 | 每个有效位置再扫一遍主导组求方差 |

合计约 2.7 万次内层操作。Python 单次列表/浮点操作约 0.4~0.5 µs，
与实测 13 ms 吻合。

其中 `float()` 调用是 Python 原型特有开销；两趟扫描、整窗重算是算法层面
的冗余，在 C++ 移植后同样存在，正是 4.4 / 4.1 要消除的对象。

## 4. 优化方向（从重到轻，向 C++ 看齐）

按**改动重量与收益量级**从重到轻排列，每项标注其对 C++ 移植的意义。

### 4.1 流式增量检测（相位锁定）—— 最重，收益最大

现状：每次检测都对完整窗口重算。滑窗每前进一帧，`drop_count` 使所有组的
边界整体移动一帧（`H=30` 时组起点绝对帧号 ≡ 最新帧号 mod 3），因此相邻
窗口的组不重叠，无法复用。

方案：把分组相位固定到绝对帧号（例如起点 ≡ 0 mod 3）。这样窗口每前进一帧
只**新增一个完整周期组、移除一个旧组**，其余 8 组完全复用：

- 特征/编码只算新组；
- 主导模式计数增量维护（新增组 +1、移除组 -1，必要时重扫）；
- CV 对主导组做增量或按需重算；
- 每块每组的持久状态约 `B×G×（3 个浮点 + 若干整型）` ≈ 几十 KB，
  完全在允许的内存范围内。

收益：特征、计数部分约降低 8~9 倍，单帧耗时预计从 13 ms 降到 1.5~2.5 ms。

**组数耦合（跳帧节奏）**：分组相位锚定在首个帧号（`phase_base`）上，
第 k 组覆盖绝对帧 `[phase_base + k*P, phase_base + k*P + P]`。每前进
P 帧（"实际增量"）恰好**新增一组**：新组 k 进窗、最旧组 k-G 出窗，
活跃组数恒为 G。实现中只在组完成帧（`(frame_id - phase_base) % P == 0`）
计算新组特征并重扫判定，中间帧只写数据、复用上一结论——即"跳帧后新的
一组做流式计算"。

**代价（必须单独设计验证）**：分组不再"对齐最新帧"，而是对齐固定相位。
对稳定周期信号结果一致；对瞬变、噪声、相位漂移信号，检测结果可能不同。
需要先用仿真数据和随机数据对照新旧两条链路的输出，确认边界后单独落地。

**C++ 对齐点**：增量维护是嵌入式 C++ 每帧处理的常态架构（每帧只处理
新增/移除的组，而不是重扫全窗）；相位锁定的持久状态直接对应 C++ 类的
成员数组，`HistoryBuffer` 的增量状态可与 C++ 结构一一映射。

**组合：流式 + 跳帧**：活跃组集合每 P 帧（P=3）才变化一次，中间两帧的
结论与上一帧完全相同。因此可叠加跳帧——只在"新组完成"的那一帧执行增量
更新与检测，其余帧直接返回缓存的上一份结论。平均每帧成本从纯流式的
1.5~2.5 ms 再降约 1/3（约 0.5~0.8 ms，另加 push_frame 写入成本）。
数据仍须每帧 push_frame，跳的只是检测调用；若前端每帧要结果对象，
中间帧复用缓存对象即可。改动量测算见第 7 节。

### 4.2 C++ 数值策略：平方比较 + 定点化 —— 重（面向 C++ 移植）

现状：CV 阶段已用平方形式推迟 `sqrt`（`pos_cv_sq = variance / mean²`），
但最终判定仍调用一次 `sqrt`；中间量保持 float 全精度。

方案分两步：

- **平方比较（Python 阶段，无语义变化）**：最终判定改为
  `max_pos_cv_sq <= max_group_amp_cv²`，彻底去掉判定路径上的 `sqrt`；
  仅 `diff_cv` 诊断输出保留一次 `sqrt`。与 C++ 的平方比较写法一致，
  改动极小。
- **定点化（C++ 移植阶段）**：把振幅、斜率、CV 中间量改为 Q 格式整数，
  先固定中间量位宽与溢出边界、对照 Python 全精度结果确认容差后再落地。

收益：Python 阶段去掉每块一次 `sqrt` 及浮点比较；C++ 阶段显著降低嵌入式
浮点/库开销。

语义变化：平方比较无语义变化；定点化有数值容差变化，需单独验证。

### 4.3 去掉热循环里的 `float()` 强制转换 —— 轻，改动小收益大

现状：特征和斜率阶段对每个差分做两次 `float()`，一个窗口约 1.4 万次
函数调用。

方案：`HistoryBuffer.push_frame()` 写入时统一转成 `float`；`detect_window()`
热循环直接做减法，int/float 混算在 Python 里语义不变（下游 `abs`、比较、
求均值都会自然得到 float）。

收益：预计减少 15%~25% 单窗耗时；**零语义变化**，测试可直接对照。

**C++ 对齐点**：C++ 的 `double history[...]` 直接做下标减法，不存在
`float()` 调用；写入时统一转 float 后，热循环写法与 C++ 一一对应。

### 4.4 CV 改为 Welford 单趟统计 —— 轻

现状：CV 先扫一遍主导组求各位置均值，再对每个有效位置扫一遍求方差，
共两趟 `O(d × P)`。

方案：Welford 单趟同时维护 `mean[p]` 和 `m2[p]`（平方偏差和），一趟扫完
主导组后直接对有效位置算 `variance = m2[p] / d`。`P=3` 很小，所有位置
都维护也几乎不增加成本。

收益：去掉约 5000 次内层操作，预计 8%~12%；数值上仍为总体方差
`ddof=0`，结果在浮点容差内不变。需要新增一个 `m2_amp[P]` 数组，内存可忽略。

**C++ 对齐点**：单趟就地累加对应 C++ 中两组数组 `mean[P]`、`m2[P]` 的
一次扫描，指令/缓存友好，循环结构可直接翻译。

### 4.5 符号编码合并进位置循环 —— 轻

现状：编码是有效组上的条件短循环（第二次扫 P 个位置）。

方案：位置循环内直接累加 `code = code * 3 + digit`。对全有效信号省一次
扫描；对噪声信号会给斜率不合格的组付出无用编码成本。收益与数据相关，
且当前实现已按设计文档保留条件短循环，**仅在 profiling 证明第二遍循环
是瓶颈后再做**。

### 4.6 其他小项 —— 最轻

- 安全剪枝：已实现（`valid_group_count <= min_match_groups` 时整块跳过），
  无需再动。
- 全门禁关闭短路：只在阈值全部禁用时生效，非默认配置，收益小。
- 入参校验 `any(index < 0 or index >= H ...)`：每调用 O(H) 次，约 30 次
  比较，占比很小，保留不优化。

## 5. 预估收益汇总

按第 4 节从重到轻的顺序：

| 优化 | 语义变化 | 预估单窗/单帧收益 | 内存增加 |
| --- | --- | --- | --- |
| 流式增量检测 | 有（分组相位锁定） | 约 5~9 倍 | 几十 KB |
| C++ 数值策略（平方比较、定点化） | 平方比较无；定点化有 | Python 微改 / C++ 阶段收益 | 无 |
| 去掉 `float()` 转换 | 无 | 15%~25% | 无 |
| Welford 单趟 CV | 无（浮点容差内） | 8%~12% | 可忽略 |
| 编码合并 | 无 | 数据相关，小 | 无 |

两项无语义变化的优化（4.3 + 4.4，另加 4.2 的平方比较收尾）叠加，
预计单帧中位数从约 13 ms 降到约 8~9 ms；再做增量检测（4.1）可进一步
降到约 2 ms 量级；若叠加跳帧（仅组完成帧执行更新），平均成本再降约
1/3（约 0.5~0.8 ms/帧，另加 push 成本）。

> 实测（30fps/50Hz、B=192、H=30，600 帧，warmup 30，周期 + 微噪声）：
> 旧全量链路每帧中位数 13.22 ms / 平均 11.41 ms；流式增量 + 跳帧后
> 每帧中位数 0.047 ms（2/3 帧为缓存命中）/ 平均 2.01 ms（约 5.7 倍）；
> 组完成帧（1/3）中位 6.72 ms——计数扫描 + CV 按需重算仍是主要开销，
> 后续可叠加 Welford / 增量计数进一步下降。

## 6. 建议实施顺序

第 4 节按重量从重到轻排列；实际实施仍按**风险从轻到重**推进，两种口径
不同，避免让最重项阻塞低风险收益。

1. **先做无语义变化的三处**：去掉热循环 `float()` 转换（4.3）+
   Welford 单趟 CV（4.4）+ 平方比较收尾（4.2 的 Python 部分），
   用现有 `tests/test_moudle1.py` 的随机对照和 30fps 仿真一致性测试
   验证结果不变，再跑基准对比。
2. **增量检测单独设计**（4.1）：先写相位锁定分组的设计与对照方案，
   确认语义边界后实现（含跳帧开关与结论节奏选择），不混入第 1 步的提交。
3. **定点化留到 C++ 移植阶段**（4.2 的 C++ 部分）：固定位宽与溢出
   边界、对照 Python 全精度结果后再落地。

## 7. moudle1.py 改动量测算

以当前 431 行为基准（`detect_window` 281 行、`HistoryBuffer` 108 行、
`main` 23 行），流式增量（4.1）+ 跳帧组合的改动以**重构**为主：核心
判定公式与语义保持不变，主要是把"每帧全量流水线"改为"按组缓存的增量
流水线"。

| 改动点 | 现状 | 改动内容 | 预估改动行数 |
| --- | --- | --- | ---: |
| 相位锁定分组 | detect_window 内约 7 行（group_starts） | 改为绝对帧号锚定；HistoryBuffer 维护相位与窗口偏移 | 10~15 |
| 持久化组状态 | 无（每次全量重算） | `__init__`/`reset` 新增 amp/sign/closure/pattern/valid 数组（B×G 级） | 25~35 |
| 特征计算 | 第 1 阶段约 51 行（B×G 循环） | 拆成"只算新组"的 helper + 缓存读取 | 30~45 |
| 主导计数 | 第 2 阶段约 39 行（每帧重建） | 增量直方图：新组 +1、旧组 -1 | 20~30 |
| CV | 第 3 阶段约 55 行（两趟） | 主导集合变化时增量维护或按需重算 | 40~55 |
| detect() 编排 | HistoryBuffer.detect 约 56 行 | 新组完成才更新，中间帧返回缓存；含跳帧开关 | 40~55 |
| 校验/输出初始化/最终判定/push_frame | 约 120 行 | 基本不动 | 0~10 |

合计：改动/重写约 200~250 行，占 431 行的 50%~58%；净增约 30~60 行
（持久状态 + 编排），改造后预计 460~490 行。

> 实际实现注记：旧版全量实现（`detect_window`/`HistoryBuffer`，431 行）
> 已在新旧对照测试通过后**删除**，`moudle1.py` 最终约 329 行，只保留
> 三个纯函数（`create_incremental_state` / `reset_incremental_state` /
> `detect_window_incremental`）。上层 API（`app/api.py`、`app/server.py`）
> 已对接：先 `create_incremental_state(params)` 创建持久状态，之后每帧
> 调用一次 `detect_window_incremental(state, blocks, frame_id)`，全部
> 计算收敛在该函数内（显式循环、固定数组），便于直译 C++；持久状态
> （dict）对应 C++ 结构体/成员数组，结论对应的相位锁定窗口由状态中的
> `window_start` / `window_end` 给出。

配套改动：

- `tests/test_moudle1.py`：新增新旧链路对照（随机数据 + 30fps 仿真
  一致性），预计 +100~150 行；
